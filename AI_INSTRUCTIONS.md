# AI Instructions for This Repository

These instructions are for Claude, Gemini, ChatGPT, or any other AI working with this repository.

## Read first

Read these files before giving strategic advice:

1. `USER_PROFILE.md`
2. `PROJECT_CONTEXT.md`
3. `CURRENT_STATE.md`
4. `DECISIONS.md`
5. The relevant file for the current task

Treat these files as the current source of truth. Do not make me repeat information already written here.

## How to answer

- Answer the request directly.
- Use simple, compact language unless detail is requested.
- Do not repeat the entire project history.
- Ask no more than one clarification question when a reasonable assumption is possible.
- Batch related work into one response instead of creating unnecessary back-and-forth.
- Do not use maximum effort for simple tasks.
- Do not browse for stable facts; browse when information may have changed or when current evidence is needed.
- For current research, cite links and dates.

## Opportunity and money research

For every proposed opportunity, evaluate:

- Customer
- Painful problem
- Existing alternatives and competitors
- Evidence of demand
- Willingness to pay
- Possible offer
- Price range and pricing assumptions
- Startup cost
- Time to first possible revenue
- Required skills
- Competition and distribution
- Main risks
- Cheapest proof-of-demand test
- Kill criteria

Never call an idea profitable without evidence. Label each important statement as one of:

- **Fact** — supported by a source or direct observation.
- **Estimate** — a numerical approximation.
- **Inference** — a conclusion drawn from facts.
- **Opinion** — a judgment or recommendation.
- **Unknown** — not established yet.

## Game-idea review

When reviewing a game idea, check:

- Player fantasy
- 30-second and 10-minute core loops
- Why a player returns tomorrow
- Differentiation from existing games
- Fun before monetization
- Scope for a small team or solo developer
- Social and replayability potential
- Onboarding and first-session clarity
- Economy and progression risks
- Ethical monetization options
- The smallest prototype that could prove or disprove the idea

Be willing to reject generic, over-scoped, grindy, or weakly differentiated concepts.

## Coding rules

- Prefer focused changes over unrelated refactors.
- Inspect only files relevant to the current task.
- Use server authority for important Roblox gameplay and economy logic.
- Use strict Luau where practical.
- Validate changes with focused tests or Studio checks.
- Do not add monetization before the core loop has been tested.

## Handoff rule

After a substantial session, update the relevant files or provide content ready to paste into them. A handoff must include:

1. Current objective
2. What was completed
3. New facts and source links
4. Decisions made
5. Ideas rejected and why
6. Open questions
7. Risks or errors
8. Exact next action

Do not invent facts or pretend that research, tests, or validation happened when they did not.
